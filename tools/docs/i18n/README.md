# Translating the docs

The user docs (`site/docs/`) are generated by `tools/docs/build-docs.mjs`. English is the source and lives in that file.
Every other language reads its text from this folder, one file per language and page:

```
tools/docs/i18n/<lang>/_site.html        header, footer, sidebar groups, banners, buttons (about 40 short strings)
tools/docs/i18n/<lang>/<page>.html       one docs page (quick-start, install, agents, …)
```

Languages are the app's 14 (`src/shared/i18n`): `en` (source), `ja`, `zh-CN`, `zh-TW`, `ko`, `es`, `fr`, `de`, `it`, `pt-BR`, `ru`, `hi`, `id`, `vi`.
English pages are published at `/docs/<page>`, the others at `/docs/<lang>/<page>`.
Anything without a translation is shown in English, with a "This page is not translated yet" notice in that language, and kept out of search engines until at least part of it is translated.

Each file can be done on its own, so one person (or agent) per language and page can work in parallel. Do `_site` first in each language: it is short and shows on every page.

## File format

```html
<!-- Ferret docs translation: ja / quick-start. … -->
<!-- @title 0000000000 -->
クイックスタート

<!-- @lead 0000000000 -->
Ferret を入れ、…

<!-- @open 0000000000 -->
## 2. プロジェクトと URL を開く
<ol class="docs-steps">
  <li><span class="docs-ui">ファイル → プロジェクトフォルダを開く…</span>（{{keys:Mod+O}}）で、…</li>
</ol>
```

- `<!-- @<id> <hash> -->` starts a unit. Keep the line exactly as it is; only the tool changes the hash.
- `title` and `lead` are plain text. Every other unit is one section: its first line is `## <heading>`, the rest is HTML.
- `0000000000` means "not translated yet": the unit is shown in English. After you translate, run `--rehash` (below) to stamp the hash of the English it was translated from.
- When the English changes later, its hash changes, the unit is treated as stale, shown in English again, and `pnpm vitest run test/unit/site` fails until it is re-translated and re-hashed.

## Rules

- **Translate** prose, headings, link text, table text, captions (`figcaption`, `alt`, `aria-label`), and the text after `|` in `{{clip:<name>|<caption>}}`.
- **Keep as is** (the test checks the first three):
  - tokens: `{{keys:…}}`, `{{keys-mac:…}}`, `{{keys-win:…}}`, `{{clip:<name>|`, `{{agent-catalog}}`, `{{path}}`, `{{relpath}}`, `{{title}}`, `{{heading}}`, `{{company}}`. Shortcuts are always written as `{{keys:Mod+Shift+R}}` and expand to both macOS and Windows / Linux; never write `⌘`, `⌥`, `⇧` or `Ctrl+…` yourself.
  - every `href` (same targets, same `#anchors`), and the HTML tags and classes.
  - `<code>`, `<pre>`, `<kbd>`, commands, paths, file names, environment variables, JSON, URLs, product and company names (Ferret, Claude Code, Codex, Gemini CLI, Ollama, GitHub, Japan Marketing LLC …).
  - Exception: the default agent instruction in `quick-start` / `agents` may be shown in the target language, because the app sends it in the display language (copy it from `agentPrompt.default` in `src/shared/i18n/<lang>.ts`).
- **UI names** in `<span class="docs-ui">…</span>` must match the app in that language. Find the English label in `src/shared/i18n/en.ts`, then use the value of the same key in `src/shared/i18n/<lang>.ts` (for example `review.sendToAgent`: "Send to Agent" → ja "Agentへ送信"). Menu paths keep the arrows: `設定 → Agent → プロジェクトを開いたら起動`.
- Quoted messages in `troubleshooting` (`<q>…</q>`) are app messages: use that language's string from `src/shared/i18n/<lang>.ts` as well.
- Keep the meaning, including limits and warnings. Don't add or drop facts. Agent-neutral wording stays neutral: "your coding agent (for example Claude Code, Codex or Gemini CLI)", not just one product.
- Keep `_site` strings short; `docs.untranslated` and `docs.partial` end with a sentence, an "English" link follows them.

## Working in parallel

Several translators (one per language) share one working tree. Only write your own `tools/docs/i18n/<lang>/` files.
Don't run the plain build (`node tools/docs/build-docs.mjs`) or `site-meta.mjs`: they rewrite `site/docs/**` and `site/sitemap.xml` for every language and collide with the others. Check your language without writing anything:

```sh
node tools/docs/build-docs.mjs --check <lang>         # stale or extra units, changed tokens or links, ⌘-style shortcuts, broken headings; exit 1 on problems
pnpm vitest run test/unit/site-docs-i18n.test.ts      # the same checks for all languages, from memory (no generated files needed)
```

Commit only your own files (`git add tools/docs/i18n/<lang> && … git commit … -- tools/docs/i18n/<lang>`). The lead runs the build and `pnpm site:meta` once after all translations are in, and commits `site/docs/` and `site/sitemap.xml`.

## Commands

```sh
node tools/docs/build-docs.mjs --scaffold <lang> <page|all>   # create the file with the English text and 0000000000 markers (adds missing units to an existing file)
node tools/docs/build-docs.mjs --rehash <lang> <page|all>     # after translating: stamp the current English hash on every unit whose text differs from English
node tools/docs/build-docs.mjs --rehash <lang> <page> --force # also stamp units that are intentionally identical to English (e.g. "macOS")
node tools/docs/build-docs.mjs --status [<lang>]              # what is missing or stale, and the size of each page
node tools/docs/build-docs.mjs --check <lang>                 # validate one language without writing anything
node tools/docs/build-docs.mjs                                # write site/docs/ (the lead runs this once; see above)
node tools/qa/site-meta.mjs                                   # update sitemap.xml (newly translated pages join it)
pnpm vitest run test/unit/site                                # stale units, tokens, links, sitemap, generated HTML
```

Only re-hash a unit after its text really matches the current English. For a stale unit, compare the English in `build-docs.mjs` (or `git log -p tools/docs/build-docs.mjs`) with your text, update it, then re-hash.

Preview locally with `node tools/qa/serve-site.mjs` and open `http://127.0.0.1:4173/docs/<lang>/<page>`.

# 03. 設計 — MOVIE-ADE

最終更新: 2026-10-02

## 1. 技術選定

### 1.1 結論

**Electron ＋ TypeScript で作る。** 重い処理（文字起こし、ターミナルのPTY）は既存のネイティブ実装を呼び出し、自前のネイティブコードは原則書かない。

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript（アプリ全体） | UI・メインプロセス・分解処理を1言語で書ける |
| デスクトップ基盤 | Electron（最新安定版） | 3つのOSに同じChromiumを同梱でき、内蔵ブラウザの表示・録画・DOM取得が同じ挙動になる |
| UI | React ＋ Vite（electron-vite） | 画面数が少なく（2モード＋一覧）、標準的な構成で足りる |
| ターミナル | xterm.js（WebGL描画）＋ node-pty | VS Code・Orca と同じ構成。GPU描画で大量出力に耐える |
| 録画 | Chromium の MediaRecorder（WebM） | 追加の依存なし。3つのOSで同じ |
| 文字起こし | 既定は whisper.cpp ＋ `large-v3-turbo`（OSごとのバイナリを同梱、モデルは初回にダウンロード）。設定で OpenAI のSTT APIに切替可（5章①） | 既定は端末内で完結し、音声が外へ出ない。macはMetalで高速 |
| LLM（指摘への整理） | Claude Code / Codex の非対話モードを子プロセスとして実行 | ユーザーのサブスクで動く。APIキー不要（6章） |
| 画像処理 | Canvas（縮小・切り抜き・合成） | ネイティブ依存なし |
| 配布 | electron-builder（dmg / exe / AppImage・deb） | 3つのOSのインストーラを同じ設定で作れる |
| テスト | Vitest（分解ロジック）、Playwright（Electron E2E） | 画面操作とスクリーンショット収集を自動化できる |
| パッケージ管理 | pnpm | — |

### 1.2 Electronでよいか（高速性の検証）

高速なADEにしたいという要件に対して、代替案と比較した。

| 案 | 起動・メモリ | 内蔵ブラウザの同一挙動 | 録画・DOM取得 | 成熟度 | 判定 |
|---|---|---|---|---|---|
| **Electron** | 起動1〜1.5秒程度、メモリは多め | ◎ 同じChromiumを同梱 | ◎ タブ録画・画面録画・DOMアクセスのAPIが揃う | ◎ Orca・VS Code・FeedbackRecorderが採用 | **採用** |
| Tauri（OS標準WebView） | ◎ 起動0.4秒程度・メモリ1/4程度（公開ベンチマークの一例） | ✕ Windows=Chromium系、mac=WebKit、Linux=WebKitGTKで表示が変わる。レビュー対象のWebがChromeと違って見える | ✕ WebKitGTKは録画・WebRTC系の機能が弱い | ○ | 「3つのOSで同じ動作」を満たせない |
| Tauri ＋ CEF（Chromium同梱） | Chromiumを積むためElectronと同等 | ◎ | △ | ✕ まだ開発ブランチ段階。Linuxでアイドル時にCPU 100%になる不具合などが未解決 | 時期尚早 |
| ネイティブ（Rust等）＋ CEF | ○ | ◎ | △ 自作が必要 | — | 3つのOS分の実装コストが大きく、「シンプルに作る」に反する |

判断の要点:

- **内蔵ブラウザにChromiumが必要な時点で、Tauriの軽さの利点はほぼ消える。** メモリと起動時間の大半はChromiumが占め、これはどの基盤でも同じ。
- **体感速度を決める処理はElectronの外にある。** 文字起こし（whisper.cpp＝ネイティブ）、LLM（外部プロセス）、PTY（node-pty＝ネイティブ）。Electronが担うのは薄いUIだけ。
- ターミナルの速さは基盤よりも描画方式で決まる。WebGL描画のxterm.jsは実績がある。
- 機能を絞っているため、Electronアプリが重くなる主因（多数のペイン、大きなUIフレームワーク、常駐処理）を持たない。

したがってElectronを採用し、**速さは目標値を決めて実測で守る**（要件 NF-3〜6）。

### 1.3 高速化の設計方針

| 対象 | 方針 |
|---|---|
| 起動（2秒以内） | 起動時に読むコードを最小化。録画・分解・過去セッション一覧は必要になった時点で読み込む。ターミナルと内蔵ブラウザは並行して起動 |
| ターミナル（遅延33ms以内） | WebGL描画。PTY出力はまとめて描画し、大量出力時は流量制御して入力を優先 |
| 録画中の軽さ | 動画エンコードはChromiumに任せる。静止画の保存は画面に変化があった時だけ。操作ログは追記のみ |
| 停止 → 下書き一覧（10秒以内） | 録画中に、無音の区切りごとに音声を切り出して逐次文字起こしする。停止時に残るのは最後の区切りだけ |
| LLM整理（60秒以内） | 既定では画像を読ませず、テキスト（文字起こし＋操作ログ）だけを渡す。高速なモデルを指定。下書きを先に表示し、結果が届いたら差し替える |

## 2. 全体構成

```
┌──────────────────────── Electron アプリ ────────────────────────┐
│ メインプロセス（TypeScript）                                      │
│  ├ ウィンドウ・モード管理                                          │
│  ├ セッション保存（.ade-movie/reviews/…）                          │
│  ├ PTY管理（node-pty）── シェル ── claude / codex（対話）           │
│  ├ 文字起こし（whisper.cpp を子プロセス実行）                       │
│  └ LLM整理（claude -p / codex exec を子プロセス実行）               │
│                                                                  │
│ UI（React）                                                      │
│  ├ エディタモード: 内蔵ブラウザ ｜ ターミナル ｜ 指摘一覧            │
│  └ フィードバックモード: 対象画面 ＋ ツールバー                      │
│                                                                  │
│ 内蔵ブラウザ（WebContentsView = Chromium）                         │
│  └ 注入スクリプト: ペン・テキストの描画、クリック・要素情報の記録     │
└──────────────────────────────────────────────────────────────────┘
```

データの流れ:

```
録画中:  画面 ─→ 動画(WebM)          マイク ─→ 音声A（自分）
         画面 ─→ 静止画(変化時)       PC音声 ─→ 音声B（相手）※MTG時
         操作・ペン・テキスト ─→ 操作ログ
              ↓ 逐次
停止後:  文字起こし（話者つき）＋操作ログ ─→ ルールで下書き ─→ LLMで整理
              ↓
         指摘一覧（確認・編集）─→ feedback.md ＋ 画像 ─→ Agent
```

## 4. 録画（フェーズ1）

録画中に4種類のデータを同じ時計（録画開始からのミリ秒）で記録する。

| データ | 取り方 | 用途 |
|---|---|---|
| 動画 | 内蔵ブラウザの内容をタブ録画（`webContents.getMediaSourceId` → `getUserMedia` → MediaRecorder）。自アプリ内の内容だけを録るため、OSの画面収録権限は不要の見込み（10章で検証） | 人間の見返し用。Agentには渡さない |
| 静止画 | `webContents.capturePage()` を0.5秒ごと（画面が変化した時のみ保存）＋ペン・テキスト確定時＋クリック時。保存時に長辺1600pxへ縮小したJPEG（1枚約60KB。原寸のままだと90分で400MBを超える） | 指摘の画像の元。動画から切り出すより鮮明で、時刻で正確に選べる |
| 音声 | マイク（自分）とPC音声（相手、MTG時のみ）を別ファイルで記録。動画にはミックスして入れる | 文字起こし。系統で話者を分ける |
| 操作ログ | 注入スクリプトとElectronのイベントから追記（JSON Lines） | URL・要素情報・直前の操作・ペンの位置 |

操作ログの例:

```jsonl
{"t":12400,"type":"nav","url":"http://localhost:3000/pricing","title":"料金"}
{"t":15820,"type":"click","x":640,"y":412,"el":{"selector":"a.nav-pricing","text":"料金"}}
{"t":18200,"type":"pen","id":"p3","t_end":19650,"bbox":[590,380,180,64],"el":{"selector":"button.plan-cta","text":"申し込む"}}
{"t":25100,"type":"text","id":"x1","x":300,"y":520,"body":"ここは「月額」表記に統一"}
```

### ペン・テキスト

- 内蔵ブラウザのページに、最前面の透明な描画レイヤーを注入する（preload で注入し、ページ本体のスクリプトとは隔離。遷移のたびに自動で再適用）。レイヤーはブラウザの Top Layer（popover）に置き、z-index の高い要素やダイアログより前に出す。スタイルはCSSOM経由で設定し、CSPが厳しいページでも動くようにする。ペンOFF時は入力を素通しし、ペンON時だけ入力を受ける。
- 描いた線・置いたテキストは画面にそのまま表示されるため、動画・静止画・画面共有のすべてに写る。画像への後合成は不要。
- ペン・テキストの位置から `elementFromPoint` で下にある要素を特定し、セレクタと表示テキストをログに残す。
- 線とテキストは、指摘の区切り（発話の区切りを検知したときに main から消去を指示）・スクロール・ページ遷移・手動の全消去で消える。指示が来ない場合の保険として上限時間でも消す。

### 音声（MTG）

- 相手の声は、PCの出力音声を取り込む（Electronの画面録画APIの音声ループバック）。取り込みの立ち上がりに0.5〜3.5秒かかるため、「相手の声も録る」がONのときは、録画開始より前にストリームを開いておく。
- マイクとPC音声を別々に文字起こしし、時刻でマージして話者つきの文字起こしにする。
- スピーカー使用時の二重取り（マイクが相手の声を拾う）は、同時刻でPC音声側と内容が重なるマイク側の発話を捨てて解消する。
- OS差: Windowsは標準で取得可能。macOSは13以降が必要で、音声取り込みの権限許可が要る。Linuxは音声サーバー（PipeWire / PulseAudio）のモニター入力を使う。**3つのOSで実機検証が必要な最大の項目**（10章）。

## 5. 分解パイプライン

```
① 素材化（決定的・端末内）   ② 下書き（ルール）      ③ 整理（LLM）          ④ 出力
 文字起こし（話者・時刻つき） → 発話のまとまり＋ペン  → 補正・除外・結合・要望化 → feedback.md
 操作ログ・静止画の時刻一覧     ＋テキストで分割        画像時刻の選択          ＋ 画像
```

### ① 素材化

- 文字起こしは実行方法を差し替え可能にする。どのエンジンも同じ `{t0, t1, speaker, text}` を返す。
- **録画中に無音区切り（2秒以上）で逐次実行する。** 停止後の待ち時間を短くするためだけでなく、品質のためにも必須（ファイル全体を一度に処理すると、無音の多い音声で同じ文を繰り返す誤認識が起き、誤り率が50%を超えた）。
- エンジンの選び方（技術検証 2026-10-02、Mac・合成音声での実測に基づく）:

| 用途 | エンジン | 理由 |
|---|---|---|
| 既定（すべての用途） | ローカル whisper.cpp ＋ `large-v3-turbo`（1.5GB） | 音声が端末外へ出ない。誤り率1.8〜3.9%、停止時に残る処理は約1秒 |
| 1人レビューを速く・高精度に（任意） | OpenAI `gpt-transcribe` | 誤り率1.7〜3.4%。時刻を返さないため、ADE側の無音区切りの時刻を使う |
| 対面MTG・マイク1本に複数人（任意） | OpenAI `gpt-4o-transcribe-diarize` | 話者分離が使える（実測で98%一致）。ローカルでは話者を区別できない |
| GPUが使えない端末（CPUのみ） | ローカル `small`（既定を自動で切替）、または OpenAI | CPUのみでは `large-v3-turbo` が実時間の0.84倍かかり、逐次処理が追いつかない（M4 ProのCPUで実測。一般的な端末ではさらに遅い）。`small` は0.32倍・誤り率4.7% |

- **オンラインMTG（マイク＋PC音声の2系統）に `gpt-transcribe` を使わない。** 区切り単位の時刻しか無く、1区間に2人の発話が混ざるため、二重取りの除去が機能しない（実測で自分の発話を15件誤って失った）。2系統でOpenAIを使う場合は、区間ごとの時刻を返すモデル（`whisper-1` など）にする。
- OpenAI を使うのは利用者が設定で選んだときだけ。選択中は「音声が外部へ送信される」ことを画面に示す。回線不調時はローカルへ切り替える。APIキーはログ・保存ファイル・エラー表示に出さない。
- 1リクエストの上限（25MB、16kHzモノラルで約13分）は、逐次処理であれば自然に満たす。

### ② 下書き（ルール。LLMなしでも成立する最低ライン）

- 発話の間隔が2秒未満なら同じまとまりにする。ただし、まとまりの長さに上限（既定30秒）を設け、超えたら内部で最も間隔が大きい箇所で再帰的に分割する（掛け合いが続くMTGで、録画全体が1つのまとまりになるのを防ぐ）。
- ペン・テキストは、時刻が重なる（または前後3秒以内の）発話のまとまりに付ける。該当がなければ単独の指摘にする。
- 画像: ペン・テキストがあればその確定時刻の静止画。なければ発話開始時刻の静止画にカーソル位置のリングを合成。まとまりの途中でURLが変わったら、変化後の静止画を追加（最大3枚）。
- 発話もペンもテキストもない区間は捨てる。

### ③ 整理（LLM）

入力（テキストのみ。1ファイル）: 話者つき文字起こし、操作ログ、下書きの指摘、静止画の時刻一覧。

LLMへの指示の要点:

- 誤変換を、画面上のテキスト（操作ログの要素テキスト・ページタイトル）と文脈から補正する。
- 指摘でない発話（独り言、つなぎ言葉、雑談）を除外する。除外したものは理由つきで別に返す（確認画面で復元できる）。
- 意味のまとまりで分割・結合する。MTGでは話題ごとにやり取りをまとめ、結論を1つの指摘にする。
- 各指摘に、見出しと要望（何をどうして欲しいか）を書く。**発話の意味を変えない。言っていない要望を足さない。**
- 結論が出ていない話題は「要確認」にする。
- 各指摘の画像にする時刻を、静止画の時刻一覧から選ぶ。

出力（JSON。スキーマで検証）:

```json
{
  "items": [{
    "title": "申し込みボタンの色が薄い",
    "request": "「申し込む」ボタンの色を濃くし、押せることが分かるようにする",
    "status": "decided",
    "quotes": [{"speaker": "相手", "t": 14200, "text": "このボタン、色が薄くて押せるように見えない"}],
    "frame_times": [19650],
    "annotation_ids": ["p3"]
  }],
  "dropped": [{"t": 9100, "text": "えーっと次は", "reason": "つなぎ言葉"}]
}
```

ADE側の検証: スキーマ、時刻が録画範囲内か、参照した発話・静止画時刻・書き込みIDが実在するか。引用と書き込みの両方が無い指摘だけを捨てる（ペンで囲んだだけ・テキストを置いただけの指摘は、発話が無くても有効）。不合格・タイムアウト・LLM未設定の場合は②の下書きをそのまま使う。

**LLMには発話の本文を書かせない。** 引用は発話の時刻（`quote_ts`）だけを返させ、本文と話者は文字起こしから引く。出力が短くなって速くなり、引用の捏造が構造的に起こらない（下のJSON例の `quotes` は、ADEが時刻から組み立てた後の形）。

### ④ 出力

- 選ばれた静止画を縮小（長辺1568pxを初期値。設定可）して `01.png …` として保存。
- `feedback.md` を生成（形式は 02_requirements.md 6章）。URL・要素・直前の操作は操作ログからADEが機械的に付ける（LLMに書かせない）。
- URL・要素・直前の操作は、発話の開始時刻ではなく**選ばれた画像の時刻**から引く（画像と説明が同じ瞬間を指すようにする。ページ遷移の完了前に話し始めると、遷移前のURLが付いてしまうため）。見出しの `[mm:ss]` は動画の頭出し用なので発話開始のままにする。確認画面で画像を差し替えたら、URL・要素・直前の操作も引き直す。
- 確認画面での編集結果は `session.json` に保存し、`feedback.md` を再生成する。

## 6. LLMの実行方法

### 既定: ユーザーのサブスクで実行（Agent CLI）

ADEが、ユーザーのPCにインストール・ログイン済みのCLIを**非対話モードの子プロセス**として起動する。修正作業をしているターミナルのAgentとは別プロセスなので、作業中のコンテキストを消費しない。

| CLI | 起動方法（確認済みのオプション） |
|---|---|
| Claude Code | `claude -p`（非対話）＋ `--json-schema`（構造化出力）＋ `--model`（高速なモデルを指定） |
| Codex | `codex exec`（非対話）＋ `--output-schema` ＋ `-o`（結果をファイルへ）＋ `--sandbox read-only` |

- 作業フォルダはセッションフォルダに限定し、読み取りのみ許可する。ツール・MCP・ユーザー設定は無効にして起動する（入力が他へ渡らないようにする）。
- **子プロセスの環境変数を掃除してから起動する。** 環境に `ANTHROPIC_API_KEY` などがあると、CLIはサブスクより先にそのキーを使い、従量課金APIで実行されてしまう。取り除くもの: `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL` 系 / `CLAUDE_CODE_USE_BEDROCK` / `CLAUDE_CODE_USE_VERTEX` / `CLAUDE_CODE_*`、Codex側は加えて `OPENAI_API_KEY` / `OPENAI_BASE_URL`。起動後、サブスクで実行されたことを結果から確認する。
- どちらのCLIが使えるかを起動時に検出し、設定で選べる。既定は Codex（所要時間が安定）、使えなければ Claude Code（sonnet）。品質は同等（05_pipeline_findings.md）。
- タイムアウトは録画の長さに応じて余裕を持たせる（8分のMTGで85〜108秒かかった）。
- 「画像も見て精度を上げる」設定をONにすると、候補の静止画も読ませる（遅くなるため既定はOFF。効果は技術検証で判定）。

### 差し替え可能な選択肢（MVPでは実装しない）

分解処理は「入力JSON → 出力JSON」の1関数として切り出しておき、実行方法だけを差し替えられるようにする。

| 方法 | 用途 |
|---|---|
| APIキー（自社またはユーザーのキー） | CLIを入れていない利用者向け |
| ローカルLLM（OpenAI互換エンドポイント） | 外部へ一切出したくない利用者向け |

## 7. Agentへの受け渡し

1. `<project>/.ade-movie/reviews/<日時>/` に `feedback.md` と画像を保存。
2. ［送信］: 内蔵ターミナルのPTYへ、次の1行を入力して実行する。送り方は先行例（Orca）の実測に合わせる（04_benchmark.md 3.3）: 送信可能な状態かを確認 → ブラケットペーストで本文だけを1回で書き込む → 50ms待つ → 状態を再確認 → Enter を別の書き込みで送る。Agent の起動直後は入力欄の準備完了を待つ。Agent が処理中のときは送ってよい（Agent側で順番待ちになる）が、権限の確認待ちのときは送らず理由を表示する。
   `"<project>/.ade-movie/reviews/<日時>/feedback.md" を読み、同じフォルダにある各指摘の画像も確認して、送信対象の指摘に対応してください。`
   文面は設定（`Settings.agentPrompt`、設定画面の Agent 欄）で変更でき、空なら上の既定文を使う。変数は `{{path}}`（feedback.md の絶対パス）と `{{relpath}}`（相対パス）。組み立ては `src/shared/agentPrompt.ts` の1か所。
3. ［コピー］: 同じ文をクリップボードへ（外部のAgent向け）。
4. 「要確認」のまま残した指摘は送信対象から外す。

Agentは `feedback.md`（テキスト）を読み、必要な画像だけを開く。動画は渡さない。ファイル経由のため、ファイルを読めるCLI Agentなら種類を問わない。

## 9. フェーズ2・3: 外部ウィンドウのレビュー

**デスクトップアプリのフィードバックは可能。** エミュレータもデスクトップ上の1ウィンドウなので、フェーズ2と3は同じ録画エンジンで実現する。ユーザーはADEの外にある実際のウィンドウをそのまま操作する。

| 要素 | 方式 |
|---|---|
| 録画・静止画 | Electronの画面録画API（`desktopCapturer`）で対象ウィンドウを取り込む |
| ペン・テキスト | 対象ウィンドウのあるディスプレイ全体に、透明・最前面・クリック素通しのウィンドウを重ねる。ペンON時だけ入力を受ける。線の座標は画像に後合成する |
| 操作 | 録画・ペン切替はグローバルショートカット。録画中は小さな常時表示バーを出す |
| ウィンドウの位置・タイトル | OSのAPIから取得（既存ライブラリを利用）。画像の切り抜きと、指摘の「アプリ名・ウィンドウタイトル」に使う |
| フィードバックモード | 対象ウィンドウ自体を画面共有する（ADEは常時表示バーとペンのレイヤーだけ） |
| 分解・確認・受け渡し | フェーズ1と同じ（URL・DOM要素の代わりにアプリ名・ウィンドウタイトル） |

### フェーズ2: スマホ（エミュレータ）

- Android Emulator: 3つのOSで対応。`adb` から表示中の画面名（Activity）と画面の要素ツリーを取得し、ペンで指した要素のID・テキストを指摘に付ける。
- iOS Simulator: macOSのみ（Xcodeの制約）。ウィンドウ録画と声・ペンは同じ。要素情報の取得は検証のうえ判断。

### フェーズ3: デスクトップアプリ

- 任意のウィンドウを対象にする。要素情報はなし（アプリ名・ウィンドウタイトル・画像・発話）。
- 画面全体が大きく文字が潰れる場合は、ペン・カーソル周辺の拡大画像を追加する。

### OSごとの制約（フェーズ2着手時に検証）

| OS | 制約 |
|---|---|
| macOS | 画面収録の権限許可が必要 |
| Windows | 特になし |
| Linux（X11） | 特になし |
| Linux（Wayland） | ウィンドウの選択がOSのダイアログ経由になる。他アプリの上への重ね表示とウィンドウ位置の取得に制約があり、ペンが使えない可能性がある |

## 10. リスクと技術検証（実装前に確認する項目）

| # | リスク | 検証内容 | だめな場合の代替 |
|---|---|---|---|
| 1 | PC音声（相手の声）の取り込みがOSで差が出る | 3つのOSでZoom / Meetの相手の声を別系統で録れるか | 仮想オーディオデバイスの案内、またはマイク1本で全員を録る運用（話者区別なし） |
| 2 | タブ録画APIの不具合報告がある | `getMediaSourceId` での録画が3つのOSで安定するか | 静止画の連番から動画を作る、またはウィンドウ録画に切り替える |
| 3 | 文字起こしの速度・日本語精度 | モデル別に、5分・30分の日本語音声で実測（Mac、Windows・LinuxのCPUのみ環境） | モデルを落とす／GPU版を使う。精度は③のLLM補正で吸収 |
| 4 | LLM整理の品質と時間 | 実際のレビュー録画とMTG録画で、指摘の漏れ・捏造・所要時間を評価。Claude CodeとCodexの両方 | 指示文の改善、画像も読ませる設定、モデル変更。最悪でも②の下書きで成立 |
| 5 | ページへの描画レイヤー注入が対象ページと干渉する | 代表的なサイト・フレームワークで表示崩れや操作不能がないか | 内蔵ブラウザの上に別の透明ビューを重ね、画像へ後合成する |
| 6 | 性能目標を守れるか | 起動時間、ターミナル遅延、録画中のコマ落ち、停止から一覧までを実測 | ボトルネックに応じて対処。目標未達なら目標値を見直して合意する |
| 7 | 画面共有との相性 | Zoom / Meet / Teamsのウィンドウ共有でフィードバックモードが正しく映るか、共有中に録画が落ちないか | 画面全体の共有を案内 |
| 8 | サブスクのCLIをアプリから呼ぶ形の利用条件 | 外部配布を決める時点で各社の条件を確認 | APIキー方式を既定にする |

### 録画エンジンの検証結果（2026-10-02、Mac・Electron 44.5.1）

| 項目 | 結果 |
|---|---|
| 動画（タブ録画） | 動作。静止ページで約0.2Mbps（90分で約134MB）、動き続けるページで約3.2Mbps（同2.0GB）。一時停止・再開、遷移をまたぐ継続、逐次書き出しを確認。リスク2の代替は不要 |
| 静止画 | `capturePage()` は中央値10ms。変化があったときだけ保存 |
| マイク | 16kHzモノラルで取得。入力レベルも取得 |
| PC音声 | macOSで取得を確認（立ち上がり0.5〜3.5秒）。リスク1はMacについては解消。Windows・Linuxは未確認 |
| ペン・テキスト・操作ログ | CSPが厳しいページ、z-indexの高い要素やダイアログがあるページでも最前面に描け、ページを壊さない |
| 時刻の一致 | 操作ログとの差は最大2ms。音声は開始の遅れを補正 |
| 録画中の負荷 | フレームレートの低下なし、CPU＋0.5〜0.8ポイント |
| ウィンドウ非表示での録画 | 動作（MTGで他のアプリを前面にしている間も録れる） |
| 異常終了時 | 強制終了しても、動画・操作ログ・静止画が途中まで残る |
| 必要な権限（macOS） | マイク＝「マイク」、PC音声＝「画面収録」。内蔵ブラウザの録画・静止画は権限不要 |

未確認: 90分の長時間録画、録画した動画の再生と頭出し、Windows・Linux。

## 12. 開発・検証の進め方

共通方針（`~/.codex/AGENTS.md` 開発方針）に従う。

- 開発・検証はMacで行う。Windows・LinuxはMac上のVMで確認し、未確認のOS・機能を合格扱いにしない。
- ブランチは `develop` と `main` のみ。通常開発は `develop` へ直接push。
- 正常系はPlaywrightによるデスクトップE2Eで操作とスクリーンショット収集を自動化し、画像を実際に見て判定する。分解ロジックは録画サンプル（文字起こし＋操作ログ）を固定入力にした単体テストで守る。
- 不具合・価値不足は、再現手順と画像を添えてGitHub Issueへ登録する。
